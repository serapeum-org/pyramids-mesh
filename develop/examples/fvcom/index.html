    Reading FVCOM native grids with pyramids-mesh¶

    FVCOM (Finite-Volume Community Ocean Model) stores its unstructured grid as a trio of ASCII files. The core one is *_grd.dat — a header with node and cell counts, then the triangle connectivity, then the node coordinates; *_dep.dat carries per-node bathymetry.

    pyramids-mesh registers an fvcom driver that parses the grid into a MeshDataset/Mesh2d. This notebook reads the chn estuarine example and walks read → explore → plot → GIS.

    2. Imports¶

    The import below is all the setup this adds: MeshDataset is the object every driver hands back (a Mesh2d or Mesh1d wrapper). Importing from pyramids also puts its vendored GDAL/PROJ data in place for you, so nothing about it is order-sensitive in a notebook -- just import the names you use.

    In [1]:
    Copied! 
    from pyramids.netcdf.ugrid import MeshDataset
import numpy as np
from pathlib import Path
import matplotlib.pyplot as plt
from cleopatra.basemap.tiles import add_tiles

    10. What needs more than a mesh¶

    • to_crs(epsg) needs a source CRS. the FVCOM grid is in projected metres but declares no EPSG code, so ds.epsg is None, so to_crs is skipped.
    • rasterize_like / regrid need a reference grid to sample onto; with only the mesh in hand there is no target, so they are out of scope for this read-only tour.

    Note — xarray interop. pyramids-core exposes a to_xarray() bridge to the xarray ecosystem, but these notebooks deliberately stay within pyramids-core's own GDAL-based UGRID I/O and do not use xarray. Its optional-dependency install hint is also currently broken upstream — tracked at serapeum-org/pyramids-core#1512.

    Takeaway¶

    MeshDataset.read_file(path, driver="fvcom") turns the native fvcom grid into a first-class pyramids mesh. Exploration, plotting, GeoDataFrame conversion, bounding polygons, connectivity analysis, spatial subsetting and export are all inherited from pyramids — pyramids-mesh only added the reader.
