    Reading OpenFOAM polyMesh directories with pyramids-mesh¶

    OpenFOAM — the open-source CFD toolbox — does not store its mesh in one file but in a polyMesh/ directory of ASCII files (points, faces, owner, neighbour, boundary). pyramids-mesh registers a driver that reads the whole directory into a single pyramids.netcdf.ugrid.MeshDataset.

    Our sample is openfoam/polyMesh (fluiddyn/fluidfoam, GPL-3.0; OpenFOAM 5.0 output): 260 points and 258 faces over a tiny domain (roughly 0.6 mm x 60 mm). It is geometry only, crs=None. Note the key difference from every other notebook: we pass the driver the directory path, not a file.

    2. Imports¶

    The import below is all the setup this adds: MeshDataset is the object every driver hands back (a Mesh2d or Mesh1d wrapper). Importing from pyramids also puts its vendored GDAL/PROJ data in place for you, so nothing about it is order-sensitive in a notebook -- just import the names you use.

    In [1]:
    Copied! 
    from pyramids.netcdf.ugrid import MeshDataset
import numpy as np
import matplotlib.pyplot as plt
from cleopatra.basemap.tiles import add_tiles

    3. Locate the sample file¶

    This notebook lives in docs/examples/, so the repo-root examples/data/ folder is two levels up. Paths are written relative to the notebook itself. OpenFOAM's mesh is a directory, so mesh_file points at the polyMesh folder itself.

    Pass a pathlib.Path, never a string. read_file keys its driver dispatch off Path objects; a bare str is not accepted.

    5. Inspect the dataset¶

    A handful of attributes describe the mesh at a glance: the node and face counts, the coordinate reference system, the list of data variables, and the planar bounding box (xmin, ymin, xmax, ymax). A CFD mesh has no geographic datum, so crs and epsg are None; the bounds are in model units (here millimetres).

    6. The underlying geometry¶

    ds.mesh is a Mesh2d. Its node coordinates live in node_x / node_y, and its face-to-node table is face_node_connectivity.data — an (n_face, k) integer array where row i lists the node indices of face i. Four node indices per row: the faces file describes mostly quadrilateral mesh faces. A winding-normalisation warning on read is expected.

    8. A filled map: projected cell area¶

    These are engineering meshes with no CRS and (usually) no field data, so there is nothing physical to colour by out of the box. A useful derived quantity is the projected 2-D area of each cell, available as mesh.face_areas. We attach it as a face variable with with_variable(...) and let plot(...) draw a filled colour map.

    The domain is sub-millimetre in X, so absolute areas are tiny (order 1e-5) — the colour map still resolves the relative variation. The very small magnitudes are a unit artefact, not an error.

    In [9]:
    Copied!

_g = ds_area.plot("cell_area", cmap="viridis", colorbar=True,

    9. The pyramids GIS toolbox applies¶

    The payoff of turning a solver file into a pyramids object is that the whole GIS toolbox now works on it, even though this is a FEM/CFD mesh. Below we exercise several operations and interpret each result.

    Export to a GeoDataFrame¶

    to_geodataframe() turns every cell into a shapely polygon inside a geopandas GeoDataFrame — the bridge to the entire vector-GIS ecosystem. Because the mesh has crs=None, the frame is unprojected (model units, not metres/degrees).

    Crop to a sub-region¶

    crop(bbox=(xmin, ymin, xmax, ymax)) keeps only the cells inside a window — the mesh equivalent of a spatial subset. Here we take the left half of the domain and re-draw it.

    What we skip, and why¶

    Because this mesh carries crs=None, the reprojection and raster-bridge operations do not apply:

    • to_crs(...) needs a source CRS to reproject from — skipped (there is no datum to interpret the model's bare coordinates).
    • rasterize_like(...) / regrid(...) burn a mesh onto, or resample it against, a georeferenced raster grid — skipped here, as there is no spatial reference to align to.

    These are first-class pyramids operations; they simply require a georeferenced mesh, which an engineering solver file is not.

    Note — xarray interop. pyramids-core exposes a to_xarray() bridge to the xarray ecosystem, but these notebooks deliberately stay within pyramids-core's own GDAL-based UGRID I/O and do not use xarray. Its optional-dependency install hint is also currently broken upstream — tracked at serapeum-org/pyramids-core#1512.

    Takeaway¶

    We read an OpenFOAM polyMesh directory (260 points, 258 faces) by passing the folder path, mapped projected cell area over its sub-millimetre domain, and ran GIS: vector export, footprint, connected components, the adjacency graph, a crop. Circumcenters are skipped (non-triangular faces).

    The pattern is always the same: MeshDataset.read_file(path, driver=...) turns a solver file into a pyramids object, and from there the full GIS toolbox applies — even for a geometry-only, CRS-less engineering mesh. pyramids-mesh contributes only the driver; every mesh operation lives upstream in pyramids.
