    Getting started with pyramids-mesh¶

    pyramids-mesh is a thin file-format layer. Hydrodynamic and hydraulic solvers each save their mesh in their own format — Gmsh .msh, SMS/TUFLOW .2dm, Telemac Selafin, DHI .dfsu, XMDF, and dozens more. pyramids-mesh registers a driver for each of these formats whose only job is to parse the file and hand back a pyramids.netcdf.ugrid object (a MeshDataset wrapping a Mesh2d / Mesh1d).

    Why does that matter? Because once the mesh is a pyramids object, the entire pyramids GIS toolbox applies — bounds, CRS handling, conversion to a GeoDataFrame, bounding polygons, circumcenters, plotting through cleopatra, and so on. pyramids-mesh adds readers, not geometry algorithms: every mesh operation lives upstream in pyramids-gis.

    This notebook walks the whole path end to end:

    1. the driver registry — how formats are discovered,
    2. MeshDataset.read_file — how a file is dispatched to the right driver,
    3. a first read → explore → plot on one real Gmsh mesh, and
    4. a couple of GIS operations that come for free from pyramids.

    1. Imports¶

    The import below is all the setup this adds: MeshDataset is the object every driver hands back (a Mesh2d or Mesh1d wrapper). Importing from pyramids also puts its vendored GDAL/PROJ data in place for you, so nothing about it is order-sensitive in a notebook -- just import the names you use.

import pandas as pd

    3. The driver registry¶

    Every supported format is a driver, discovered through Python entry points and collected by mesh_drivers(). It returns a plain dict mapping a short driver name to its driver class. The number of entries is simply how many formats this install can read or write.

    4. What a driver advertises¶

    Each driver class exposes four descriptive attributes:

    • .name — the short key used in the registry and for forcing a driver,
    • .long_name — a human-readable format name,
    • .suffixes — the file extensions it claims, and
    • .capabilities — a set of verbs describing what it can do with that format.

    We inspect the Gmsh driver, since that is the format we are about to read.

    In [4]:
    Copied! 
    gmsh = drivers["gmsh"]
{
    "name": gmsh.name,
    "long_name": gmsh.long_name,
    "suffixes": gmsh.suffixes,
    "capabilities": sorted(gmsh.capabilities),
}
    gmsh = drivers["gmsh"] { "name": gmsh.name, "long_name": gmsh.long_name, "suffixes": gmsh.suffixes, "capabilities": sorted(gmsh.capabilities), }
    Out[4]:
    {'name': 'gmsh',
 'long_name': 'Gmsh mesh',
 'suffixes': ('.msh',),
 'capabilities': ['read_mesh']}

    The capabilities are the vocabulary to read the whole table next:

    • read_mesh / write_mesh — load or save the topology (nodes + faces),
    • read_data / write_data — load or save field values attached to the mesh,
    • multi_mesh — the file can hold more than one mesh, and
    • lazy_data — field values can be read on demand rather than all at once.

    So a format tagged only read_mesh gives you geometry but no solver results — exactly the Gmsh case.

    Scanning the capabilities column: most drivers are importers (read_mesh), a solid subset also round-trips field data (read_data + write_data), and only a handful advertise multi_mesh or lazy_data. This single table is what "supports N formats" actually means in code.

    6. Reading a file: automatic dispatch¶

    MeshDataset.read_file(path) is the one entry point you normally call. It inspects the file's suffix and content, finds the matching driver in the registry, and runs it — you do not name a driver yourself. The result is a MeshDataset.

    In [6]:
    Copied! 
    ds = MeshDataset.read_file(mesh_file)
type(ds)
    ds = MeshDataset.read_file(mesh_file) type(ds)
    Out[6]:
    pyramids.netcdf.ugrid.dataset.MeshDataset

    read_file saw the .msh suffix, routed to the gmsh driver, and returned a fully-formed MeshDataset — the same type pyramids produces from a NetCDF UGRID file. From here on, nothing in the API knows or cares that the data originated as Gmsh.

    7. Forcing a specific driver¶

    When a suffix is ambiguous (several formats share .inp or .nc, for instance) you can override auto-detection with the driver= argument, naming any key from the registry. Here we force gmsh explicitly and confirm we get the identical mesh.

    In [7]:
    Copied! 
    ds_forced = MeshDataset.read_file(mesh_file, driver="gmsh")
ds.n_face == ds_forced.n_face
    ds_forced = MeshDataset.read_file(mesh_file, driver="gmsh") ds.n_face == ds_forced.n_face
    Out[7]:
    True

    Same face count — forcing the driver produced the same result as auto-detection. The driver= escape hatch is there for the ambiguous-suffix cases, not needed for a clear one like .msh.

    8. Exploring the dataset's metadata¶

    A MeshDataset exposes summary properties that describe the mesh as a whole. The most useful on a first look:

    • n_node / n_face — size of the mesh,
    • crs / epsg — the coordinate reference system, if the format recorded one,
    • bounds — the spatial extent (minx, miny, maxx, maxy), and
    • data_variable_names — names of any field variables attached to the mesh.

    11. The underlying Mesh2d¶

    ds.mesh is the Mesh2d object holding the raw topology. The arrays you reach for most often:

    • node_x / node_y — node coordinates,
    • face_node_connectivity.data — the (n_face, k) table of node indices per face, and
    • face_areas — area of each face.
    In [11]:
    Copied! 
    mesh = ds.mesh
conn = mesh.face_node_connectivity.data
{
    "n_node": mesh.node_x.shape[0],
    "connectivity_shape": conn.shape,
    "face_areas_shape": mesh.face_areas.shape,
}
    mesh = ds.mesh conn = mesh.face_node_connectivity.data { "n_node": mesh.node_x.shape[0], "connectivity_shape": conn.shape, "face_areas_shape": mesh.face_areas.shape, }
    Out[11]:
    {'n_node': 67, 'connectivity_shape': (111, 3), 'face_areas_shape': (111,)}

    The connectivity shape (n_face, k) is the heart of an unstructured mesh: row i lists the node indices that form face i. The second dimension k is the max nodes per face (triangles pad unused slots). Everything geometric — areas, centroids, the outline — is derived from this table plus the node coordinates.

    12. First plot: the mesh outline¶

    The simplest visualization needs no data at all -- just draw the wireframe with plot_outline(), which renders the mesh edges through cleopatra and returns a MeshGlyph wrapping the figure. Reading the file above flipped matplotlib to a non-interactive backend, so we let cleopatra choose it with Config.set_matplotlib_backend() (which picks inline in a notebook); from now on every plot embeds on its own.

    add_tiles(_g.ax, crs=ds.epsg)
    from cleopatra.config import Config Config.set_matplotlib_backend() # cleopatra picks the inline backend in a notebook _g = ds.plot_outline() if ds.epsg: add_tiles(_g.ax, crs=ds.epsg)

    This is the mesh as the solver sees it — an unstructured grid of triangular cells, finer where the geometry demands resolution. Seeing the wireframe is the fastest sanity check that a file read in correctly.

    13. A data map: attach and plot a field¶

    To draw a filled map we need a value per cell. This mesh has none, so we compute one — each cell's area — and attach it with with_variable(..., location="face"), which returns a new dataset carrying that field. (The original ds is left untouched.)

    d2 now has a face-located variable called cell_area. Because it is a normal pyramids field, we can colour the mesh by it.

    In [14]:
    Copied!

    Each cell is now shaded by its area: darker cells are smaller (the refined regions), brighter cells larger (the coarse interior). This is the generic pyramids data-map path — any per-cell field, from water depth to velocity, plots the same way.

    Because the mesh is a pyramids object, pyramids' GIS layer applies directly. A few teasers:

    Circumcenters¶

    circumcenters() returns an (n_face, 2) array of per-cell circumcenter coordinates — the points a finite-volume scheme places unknowns at. It is a mesh-derived geometry pyramids computes on demand.

    In [18]:

    cc = ds.circumcenters() cc.shape, cc[:3]
    Out[18]:

 array([[-0.25617308,  0.62151923],

        [-0.10250116,  0.58672018]]))

    (n_face, 2) — one (x, y) per cell. That these derived quantities are a method call away is the whole point of turning the file into a pyramids object.

    Takeaway¶

    • pyramids-mesh is a format layer: drivers parse mesh files into pyramids.netcdf.ugrid objects, and that is all they do — no GIS, no interpolation, no analysis.
    • mesh_drivers() is the registry of every supported format, each driver advertising its suffixes and capabilities.
    • MeshDataset.read_file(path) auto-dispatches to the right driver by suffix/content, with driver= as an override.
    • Once read, the mesh is a first-class pyramids object: explore it (n_node, bounds, summary()), plot it (plot_outline, plot), and run GIS operations (to_geodataframe, bounding_polygon, circumcenters) — all from pyramids, not from this package.

    Next: see the per-format and domain notebooks in docs/examples/ for reading specific solver outputs (2DM, Selafin, DFSU, …), attaching real result fields, and the deeper GIS workflows pyramids provides.
