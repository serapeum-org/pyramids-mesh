    3Di results with pyramids-mesh¶

    3Di is a hydrodynamic flood model whose results NetCDF stores values on a staggered sub-grid rather than an explicit polygon mesh. The pyramids-mesh 3Di driver is a needs-mesh driver: it reconstructs the 2D cell grid itself from the file's geometry arrays, then presents it as a standard MeshDataset.

    (3Di files can also carry a coupled 1D network; pyramids represents the 2D mesh and warns that the 1D part is dropped.)

    Explore the dataset¶

    A MeshDataset wraps a UGRID-style unstructured mesh plus any data variables that ride on it. The scalar properties below describe the grid at a glance: how many nodes and faces it has, its coordinate reference system, and its spatial extent.

    The reconstructed grid here is a compact 4x4 block of quad cells (25 nodes, 16 faces).

    crs/epsg are often None: many hydraulic-model result files store coordinates without an embedded CRS, so pyramids reports the geometry faithfully and leaves georeferencing to you. The bounds tuple is the mesh envelope in the file's own coordinate units.

    From mesh to GIS¶

    A MeshDataset is not a dead end - it converts into the vector and raster types the rest of a GIS workflow expects. Everything below is reached through pyramids; this package only supplies the file-format driver that built the mesh.

    Circumcenters - not applicable here¶

    circumcenters() is only defined for purely triangular meshes. This grid contains quad (or mixed-polygon) faces, so the call would raise ValueError. We note it and skip rather than force it.

    Self-contained rasterisation¶

    to_dataset(variable, cell_size=...) samples the mesh onto a regular raster grid and returns a pyramids Dataset. Unlike rasterize_like / regrid — which need an existing reference grid — this is self-contained: pick a cell size and pyramids builds the grid. We derive the cell size from the average face area so the raster has sub-face resolution regardless of the mesh density.

    In [21]:
    Copied! 
    # derive cell size from the mesh resolution (~half an average face edge)
cell_size = float(np.sqrt(ds.mesh.face_areas.mean())) / 2
rast = step.to_dataset("Mesh2D_s1", cell_size=cell_size)
print("rasterised to:", type(rast).__name__)
rast.plot()
plt.title("Mesh2D_s1 rasterised")

    Reprojection - skipped¶

    to_crs(...) needs a source CRS to project from. This 3Di result stores coordinates without a CRS, so ds.crs is None. With no source CRS, reprojection is undefined, so we skip it; assign a CRS first if your coordinates are georeferenced.

    Note — xarray interop. pyramids-core exposes a to_xarray() bridge to the xarray ecosystem, but these notebooks deliberately stay within pyramids-core's own GDAL-based UGRID I/O and do not use xarray.

    Takeaway¶

    The 3Di driver shows what a needs-mesh driver does: the file never stored an explicit polygon mesh, yet the driver reconstructs the 2D grid and serves it as an ordinary MeshDataset. Select a wet timestep with isel, then map water level and volume, convert faces to vectors, or crop - all through the shared pyramids API, with the 1D network reported-but-skipped rather than silently mangled.
